# 性能测试模块

三种运行方式，场景配比完全一致，便于交叉验证结论。

| 方式 | 命令 | 适用 |
|---|---|---|
| 内置执行器（推荐） | `python perf/run_load_test.py --users 20 --duration 10` | 自带被测服务、自动出 Markdown 报告与曲线，可进 CI |
| locust | `python -m locust -f perf/locustfile.py --host http://127.0.0.1:8000` | 需要 Web UI、实时曲线、分布式压测 |
| JMeter | 先 `python -m mock_server.app`，再打开 `perf/jmeter/device_api.jmx` | 团队已有 JMeter 体系、需要出 jtl 结果文件 |

> 内置执行器会自动在随机端口拉起 Mock 服务，无需手工启动；locust 与 JMeter 需要先起服务。

## 一、场景设计

### 1.1 为什么这样配比

| 场景 | 权重 | 理由 |
|---|---|---|
| 上报数据 `POST /api/readings` | 55% | 设备侧的真实行为是"周期性上报"，写请求占大头，也是最先被压垮的接口 |
| 查询数据 `GET /api/readings` | 30% | App 端拉取历史曲线 |
| 查询汇总 `GET /api/devices/[sn]/summary` | 15% | 首页概览，聚合计算，CPU 敏感 |

**不要所有线程都压同一个接口**——那测出来的是单接口极限，不是系统容量。

### 1.2 三个必须设置好的参数

1. **思考时间（think time）**：默认 50~200ms。不加思考时间，20 个线程等于 20 个请求同时打，压力被放大数倍，测出来的瓶颈是假的。
2. **参数化**：每台虚拟设备注册独立 SN，数据用随机温度/电量/心率。**用同一个 SN 循环上报会命中唯一键冲突或缓存，结果不可信。**
3. **阶梯加压**：`--ramp 5` 表示 5 秒内把用户铺开，而不是瞬间全上。瞬间全上是"冲击测试"，观察不到随并发增长的性能曲线。

### 1.3 关于时间戳

上报数据以 `(sn, ts)` 做幂等去重，压测时必须保证 `ts` 唯一，否则会被服务端判为重复上报、200 返回，TPS 看起来很高但实际没写入——**这是压测里最隐蔽的坑之一**。脚本里用「虚拟用户序号 × 1000000 + 自增序号」保证唯一。

## 二、通过判据

| 指标 | 阈值 | 说明 |
|---|---|---|
| 错误率 | ≤ 0.1% | 业务失败（断言失败）必须为 0 |
| P95 响应时间 | ≤ 500 ms | 上报类接口偏宽松，查询类可收紧到 200 ms |
| TPS | 随并发线性增长 | 出现平台期即拐点，记录该并发数 |
| 资源 | CPU ≤ 70%，内存无持续增长 | 本仓库未接监控，接入真实服务时补 Prometheus |

## 三、实测输出示例

`--users 20 --duration 10 --ramp 5`：

```
总请求数 2071     平均 TPS 205.88
平均 RT 17.1ms    P50/P95/P99 = 16.0 / 36.8 / 46.7 ms
错误率 0.0%
```

产物：

- `reports/perf_report.md` —— 测试条件、总体结果、分场景、判据与结论
- `reports/perf_throughput.png` —— TPS 与 P95 随时间双曲线
- `reports/raw/perf_summary.json` —— 原始指标，便于入库做趋势对比

## 四、必须说清的局限

1. **被测服务是单进程内存实现**，瓶颈通常先出现在被测端（GIL + 单进程），而不是网络或数据库。这个结果用于**验证压测脚本与指标口径**，不代表真实后端容量。
2. **压测机与被测服务同机**，CPU 竞争会让 P95 偏高。真实压测要把压测机独立出来，走真实网络。
3. **数据量级不同**：内存里几百条，真实库可能几百万条，查询性能不可类比。

面试时主动说这三点，比报一个好看的 TPS 更可信——**能说清"这个数不能用来下什么结论"，才是做过压测的人**。
