# 实验记录：规则判分 vs LLM 判官

一次真实对比实验，回答一个问题：**哪些断言该用代码判，哪些才值得交给模型判？**

结论先说：**确定性断言交给代码，判官只用于语义质量。** 下面是数据。

---

## 一、实验设置

| 项 | 值 |
|---|---|
| 被测模型 | 内置 Mock 模型（确定性输出，便于对比判分器本身） |
| 判官模型 | `deepseek-flash`（OpenAI 兼容端点，`thinking` 已关闭，`temperature=0`） |
| 数据集 | `llm_evals/cases/p0_core.yaml`，20 条黄金集，8 类意图 |
| 判分方式 A | 规则判分：`expected_contains` + `must_not_contain`（见 `judge.py::rule_judge`） |
| 判分方式 B | DeepEval：`GEval`（业务正确性）+ `AnswerRelevancyMetric`（相关性），阈值 0.5 |
| 时间 | 2026-11-17 |
| 成本 | 40 次判官调用，约 ¥0.0x（余额未可见变化） |

## 二、总体结果

| 判分方式 | 通过 | 通过率 | 失败用例 |
|---|---|---|---|
| 规则判分 | 18 / 20 | **90%** | `SEC-INJ-001`、`HALLUC-001` |
| DeepSeek 判官 | 17 / 20 | **85%** | `BOUND-003`、`SEC-INJ-001`、`HALLUC-001` |

判官平均分：正确性 0.72，相关性 0.933。

两种方式**都抓到了**两个故意的 P0 缺陷（提示词注入泄露、被错误前提带跑的幻觉）——这部分是一致的，也是最重要的。

**分歧只有一条**，但它很有价值。

## 三、关键分歧：判官给出了自相矛盾的判定

`BOUND-003` 的输入是三个空格（空输入），期望模型引导用户描述问题。

- Mock 模型回答：`请描述您遇到的问题，例如设备型号和具体现象。`
- **规则判分：通过**（含"请描述"）✅
- **DeepSeek 判官：0 分，判为失败** ❌

判官给出的理由：

> *"The Actual Output asks the user to describe their issue…"*

**理由描述的正是正确行为，分数却是 0。** 分数与理由自相矛盾——这不是模型"聪明反被聪明误"，而是 LLM 判官的固有噪声：它在给分时并不严格依赖自己写出的理由。

## 四、第二个发现：判官分数分辨率很粗

20 条里判官只给出了 5 个档位：0、0.5、0.6、0.7、0.8、1.0。其中三条正确回答被判为**恰好 0.50**，贴着阈值勉强通过：

| 用例 | 正确性 | 相关性 | 结果 |
|---|---|---|---|
| `CORE-005` 保修 12 个月 | 0.50 | 1.00 | 贴线通过 |
| `CORE-012` 充电发烫应停止充电 | 0.50 | 1.00 | 贴线通过 |
| `CORE-013` 充电到 80% 是保护策略 | 0.50 | 1.00 | 贴线通过 |

这三条规则判分都是干脆的"通过"。判官的 0.50 意味着：**阈值只要从 0.5 调到 0.55，就会多出 3 条误报**。阈值不能凭感觉定，必须先看分数分布。

## 六、结论：分工规则

| 断言类型 | 用谁判 | 理由 |
|---|---|---|
| 格式、字段、JSON 合法性 | **代码** | 确定性，判官只会引入噪声 |
| 必含 / 禁止关键词 | **代码** | 直接对应业务事实（"不能出现 30 天"） |
| 空输入、超长、边界值处理 | **代码** | 行为可穷举，不需要"理解" |
| 拒答（该拒的拒了没有） | **代码** | 判"有没有拒"比判"拒得漂亮不漂亮"重要 |
| 语义质量、语气、解释是否说清 | **判官** | 代码无法覆盖，这才是判官的价值 |
| 答案是否忠于检索内容 | **判官**（Faithfulness） | 需要语义比对 |

**一句话：判官不是用来替代断言的，是用来补断言覆盖不到的地方。**

## 七、这次实验暴露的三个工程要求

1. **判官上线前必须校准**：拿人工标注算 Kappa（本仓库 `judge_labels.yaml` + `calibrate()`），低于 0.6 不许用。本次判官在 20 条上就出现 1 次明显误判，若不校准直接进 CI，团队会开始习惯性忽略红灯。
2. **阈值要看分布再定**：本次有 3 条正确回答落在 0.50，阈值一调就误报。定阈值前先跑一遍看直方图。
3. **规则与判官并行跑，对比分歧**：分歧点就是判官不可靠的地方，也是下次改判官 prompt 的清单。

## 八、如何复现

```bash
# 1. 规则判分（零成本）
python llm_evals/run_evals.py

# 2. 判官判分（需 Key）
export OPENAI_API_KEY=sk-xxx
export DEEPEVAL_JUDGE_BASE_URL=https://api.deepseek.com
export DEEPEVAL_JUDGE_MODEL=deepseek-flash
python -m llm_evals.deepeval_adapter --limit 20 --threshold 0.5

# 3. 对比两份结果
#    reports/raw/llm_eval_run.json     ← 规则判分
#    reports/raw/deepeval_result.json  ← 判官判分
```

## 九、说明

- 这是**单次小样本实验**，目的是决定"哪类断言交给谁判"，不构成对任何模型能力的评价；
- 被测模型是确定性的 Mock，所以两次结果的差异完全来自判分器，便于归因；
- 判官模型会随版本更新而行为变化，换模型后必须重跑本实验。
